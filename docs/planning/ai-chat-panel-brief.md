**Key UX requirement — globally accessible:** the chat panel must be reachable **from any desk view** — not buried in a single workspace or page. Use the industry-standard pattern: a persistent launcher (floating action button / docked side rail) present on every route, opening a slide-over or dockable panel that preserves conversation state as the user navigates between Forms, Lists, Reports, and Workspaces. Follow established best practices for in-app AI assistants (persistent affordance, non-blocking slide-over, streaming responses, keyboard shortcut to toggle, conversation history, graceful loading/error states, mobile-responsive). Survey how comparable products and ERPNext's own global UI (navbar/awesomebar) mount globally, and choose the approach idiomatic to Frappe's desk rather than a one-off page.

**Key UX requirement — context-aware of the current record:** the panel must automatically know what the user is currently looking at and make that the working context, without the user pasting IDs. Specifically:
- When the user is on a **Form view**, the panel knows the current DocType, document name, and (within permission limits) the on-screen field values — so "summarize this", "what's wrong with this invoice", "email the supplier on this PO" just work against the open record.
- When on a **List/Report view**, it's aware of the DocType and the active filters so the user can ask about the visible result set.
- The context must **update live** as the user navigates (route change → context refresh) and be **clearly displayed** in the panel ("Context: Purchase Invoice ACC-PINV-0001") with a way to clear/pin it.
- **Security caveat for context:** the captured context is a *convenience hint*, never an authorization bypass — every actual data read/write still goes through the server-side permission-checked path below. The client-supplied context (DocType + name) must be **re-validated and re-fetched server-side under the calling user's permissions**; never trust field values sent from the browser as ground truth for a write. Investigate the supported Frappe client API for reading the current route/form (`frappe.get_route`, `cur_frm`, `frappe.ui.form` events, router change events) and cite it.

**Phase 2 — Security design (this is the priority, be explicit):**
Address each of these and cite the Frappe permission/auth docs for the mechanisms you choose:
- **Authentication:** the panel works only for an authenticated desk session; spell out how the backend verifies `frappe.session.user` and rejects guest/unauthenticated calls. No anonymous access, no API key in the browser.
- **Authorization / RBAC:** Claude's tool calls against MCP/ERPNext data MUST be constrained to what the *calling user* is permitted to see and do — never broader. Define how each tool invocation runs in the calling user's permission context (not as Administrator), how `frappe.has_permission` / user-permission filters / role checks apply, and what happens on denial.
- **Context re-validation:** restate explicitly that the client-supplied current-record context is re-validated and re-fetched server-side under the user's permissions before any read/write; browser-sent field values are never trusted for writes.
- **Secret handling:** the Claude API key and MCP credentials stay server-side only; describe the trust boundary (browser → whitelisted Frappe endpoint → server-side Claude call → MCP) and confirm the key never reaches the client.
- **Guardrails:** rate limiting, audit logging of who asked what and which tools ran (and against which record), prompt-injection considerations for tool results and document content flowing back into the model, and whether write-capable MCP tools should be gated behind confirmation or a role.
- **A threat model table:** for each attacker (curious low-privilege user, compromised session, prompt injection via document content, forged/escalated context payload), state the mitigating control.
