1. What ERPNext Is

ERPNext is a 100% open-source, full-stack ERP delivered as a single Python package (erpnext) that plugs into a Frappe Bench. It covers accounting, stock, manufacturing, selling, buying, projects, assets, CRM, support, quality, subcontracting, EDI, regional tax/compliance, and a portal/website.

ERPNext does not run standalone. The Frappe Framework hosts it and provides:

  • The persistent DocType model (metadata-driven schemas → MariaDB tables).
  • DB abstraction (frappe.db, frappe.qb), auth, roles, workflows.
  • REST/RPC API (/api/method/*, /api/resource/*).
  • Background job queue (RQ over Redis) and a cron-like scheduler.
  • The desk UI, portal/website rendering, print, email, file storage, test runner.

"ERPNext" is therefore best read as business doctypes + controllers + reports + hooks layered on top of Frappe.

                       │                                       │               │
   Email / Cron ─────► │  Frappe Scheduler ─► RQ workers ──────┘               │
                       │            │                                          │
                       │            ▼                                          │
                       │  MariaDB  ◄──►  Redis (cache + queue + websocket)     │
                       │            ▲                                          │
                       │            │                                          │
                       │  File storage (private/public)                        │
                       └──────────────────────────────────────────────────────┘
  • Web tier: Nginx in front of Gunicorn workers running the Frappe Werkzeug app.
  • Async tier: Frappe scheduler enqueues into Redis-backed RQ; workers consume default, short, long. ERPNext registers callbacks under scheduler_events in hooks.py.
  • Persistence: MariaDB is canonical; each DocType becomes a tab<DocType> table. Redis is cache + websocket bus, not source of truth.
  • Files: the Frappe File doctype wraps uploads on disk (or S3). Used by the fork's Document Capture.
  • Realtime: Socket.IO via Frappe for desk notifications and live document updates.

4. Core Architectural Concepts

4.1 DocType — the universal building block

Every business object — a Customer, a Sales Invoice line, a setting page, a workflow state — is a DocType. Each is defined by a JSON descriptor (fields, naming rule, permissions, child tables) plus an optional Python Document subclass for behavior. Document lifecycle: 

before_insert → validate → before_save → after_save → on_update
                                       └─ on_submit → on_cancel → on_trash

Cross-doctype reactions are wired in hooks.py:doc_events — e.g. wildcard * validators apply SLA and the transaction-deletion lock to every save; the 17 period_closing_doctypes get an accounting-period guard; Stock Entry submit/cancel recomputes linked Material Request fulfillment.

4.2 Controllers (cross-doctype mixins)

ControllerRole
AccountsControllerBase for any GL-posting document (Sales/Purchase Invoice, Payment Entry, Journal Entry). Posting date, currency, tax orchestration, payment schedule, advances.
BuyingController / SellingControllerPurchase/sale-side shared logic — party validation, pricing rules, item defaults.
StockControllerAnything that creates Stock Ledger Entries (Stock Entry, Delivery Note, Purchase Receipt, Subcontracting Receipt).
SubcontractingControllerThe special inventory/cost flow for outsourced manufacturing.
TaxesAndTotalsThe single tax/total recomputation engine called by every transactional controller.
StatusUpdaterRecomputes Billed / Delivered / Completed status percentages on parent documents from child rows.

                                        │            Payment       Payment

                                        ▼
                                  Stock Ledger Entry (Bin)

                                                        │
                                                        ▼
                                          Purchase Receipt ─► Purchase Invoice ─► Payment Entry
                                                  │                  │                  │
                                                  ▼                  ▼                  ▼
                                              SLE + Bin        GL + PL Ledger     GL + PL Ledger
  • GL Entry is the journal-line truth; Payment Ledger Entry is a parallel AR/AP-perspective ledger that powers receivable/payable reports without re-scanning GL.
  • Period Closing Voucher snapshots a year's P&L into Account Closing Balance.
  • Accounting Dimensions (Cost Center + arbitrary additional dimensions) flow through every GL Entry and ~50 transaction doctypes — see accounting_dimension_doctypes in hooks.py.
  • Bank reconciliation is its own subsystem (Bank Reconciliation Tool, Bank Transaction, Bank Clearance). Whether a payment is reconciled is a separate signal from whether the AR/AP is settled.

4.4 Stock / inventory engine

  • Stock Ledger Entry is append-only; quantity and valuation are derived from it.
  • Bin caches per-(Item, Warehouse) on-hand state for fast lookups.
  • Repost Item Valuation is the queued job that recomputes SLE valuation when historic stock is edited; runs every 30 min via scheduler_events.cron and on demand.
  • Serial No / Batch No / Serial and Batch Bundle track identity-bearing inventory.

4.5 Manufacturing

BOM (version + cost-update every 15 min) → Production Plan → Work Order → Job Card → Stock Entries (Manufacture / Material Transfer for Manufacture).

4.7 Regional / multi-jurisdiction

erpnext/regional/<country>/utils.py ships per-country overrides registered via regional_overrides and direct doc_events: Italy (FatturaPA e-invoice, state code on Address), UAE/Saudi Arabia (reverse-charge VAT, itemised tax data, regional GL entries), France (regional test hooks).

4.8 Background processing & scheduler

  • Every 15 min: BOM cost-update job resumer.
  • Every 30 min: parallel reposting of item valuation.
  • 30 past the hour: GLE/SLE rename queue.
  • Hourly: project deadline reminders.
  • Hourly maintenance: repost valuation, bulk-transaction retries, project status, Plaid sync, YouTube data.
  • Daily maintenance: ~25 jobs — auto-close tickets, update invoice statuses, fiscal year auto-create, supplier scorecards, asset maintenance/depreciation posting, dunning, reorder, subscriptions, e-mail digests.
  • Weekly / Monthly long: exchange rate revaluation, deferred revenue/expense processing.

4.9 Test architecture

  • Module-local test_<doctype>.py via frappe.tests.IntegrationTestCase against MariaDB.
  • before_tests = erpnext.setup.utils.before_tests bootstraps _Test Company, _Test Item, _Test Supplier, _Test Bank - _TC, _Test Cost Center - _TC, etc.
  • Tests roll back with frappe.db.rollback() in tearDown.

4.10 Frontend

ERPNext does not ship a separate SPA. The desk UI is delivered via Frappe with ERPNext contributing esbuild bundles (declared in package.json), DocType-attached client scripts (erpnext/public/js/*.js and per-doctype *.js), a small Vue / Frappe-UI surface for POS, plus server-rendered Jinja for portal/website pages.

6. Data Flow Examples

6.1 Submit a Purchase Invoice (the AP path the fork extends)

  1. User or API creates a Purchase Invoice referencing a Supplier and items.
  2. BuyingController.validate → TaxesAndTotals recomputes totals; AccountsController.validate checks posting date / accounting period.
  3. The period_closing_doctypes validator confirms the date isn't in a closed period.
  4. On submit: make_gl_entries posts journal lines to GL Entry + parallel Payment Ledger Entry, advances Payment Schedule, updates Supplier outstanding.
  5. StatusUpdater updates the linked PO / Purchase Receipt billed-status.
  6. Reports (Accounts Payable, Trial Balance) read from GL Entry + Payment Ledger Entry.

6.2 Settle a Purchase Invoice via Payment Entry

  1. get_payment_entry("Purchase Invoice", pi.name, …) prefills a draft PE.
  2. On submit: GL Entries debit Creditors, credit the bank account; PI outstanding_amount → 0; PI status → Paid.
  3. No Bank Transaction is created by Payment Entry submission. Bank Transactions originate from bank statement import / Plaid; Bank Reconciliation Tool links them to PEs afterwards.
Settlement vs. reconciliation. A submitted Payment Entry with a PI outstanding_amount = 0 means the payable is settled. Whether a real bank statement line has been matched to that PE is a separate signal carried by Bank Transaction + Bank Reconciliation Tool. The AP Closed Loop fork intentionally never crosses into Bank Transaction territory.

8. Extension Points

  1. Add a DocType JSON + Document subclass under erpnext/<module>/doctype/<name>/.
  2. Wire cross-doctype reactions through hooks.py:doc_events rather than monkey-patching.
  3. Whitelisted server methods (@frappe.whitelist()) become RPC endpoints at /api/method/erpnext.<path>.<fn> — this is how the AP Closed Loop pilot exposes its actions.
  4. Reports go under <module>/report/<name>/ (*.json, *.py, *.js).
  5. Workspaces & dashboards under <module>/workspace/ and <module>/dashboard_chart/.
  6. Country-specific behavior under erpnext/regional/<country>/ + hooks.py:regional_overrides.
